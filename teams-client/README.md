# Teams Client

Teams Client uses the pinned `@pnp/cli-microsoft365` v11.11.0 package from a plugin-owned runtime directory and calls its delegated Teams commands. It never installs m365 globally. The package's npm tarball integrity is `sha512-GXdN3Cw4lOEFixVfI6YZlGM9OzAlMbjGItT8yMn8FznlG6+aWGNI6xjgNJRbigykeSE6YI3KRai+fijMt24DMg==`; the same platform-independent package checksum is checked for each supported OS and architecture. Node.js 20 or later and npm must be available. Supported targets are macOS, Linux, and Windows on x64 and arm64.

`osodevops/ms-teams-cli` remains a re-evaluation candidate for a later pass. It was v0.9.0 and too young for the owner's work account when this dependency choice was made.

The runtime and isolated m365 home are under the plugin-owned data root, the host's per-instance plugin data directory; on a dev instance `~/.codeterm` below means `~/.codeterm-dev` (or `~/.codeterm-dev-<name>`). On macOS and Linux they are `~/.codeterm/teams-client/runtime/m365` and `~/.codeterm/teams-client/m365-home`. On Windows they are `%USERPROFILE%\.codeterm\teams-client\runtime\m365` and `%USERPROFILE%\.codeterm\teams-client\m365-home`. Both `HOME` and `USERPROFILE` point to the isolated home on every CLI call, alongside platform-specific config-home variables. This keeps the plugin's sign-in, connections, and tokens separate from the owner's own m365 profile. POSIX directories are restricted to mode 0700 and cache files to 0600. Windows applies an owner and SYSTEM ACL with `icacls`; POSIX modes are not used as a Windows security claim. The resolver and package integrity map cover macOS, Linux, and Windows on x64 and arm64; the npm package is platform-independent, so the verified SRI is the same for all six supported target keys. Other OS/architecture pairs receive a named unsupported-target state.

The required `node` subprocess permission identifies the runtime and verifies the locally packed tarball checksum. Filesystem-confinement statements describe plugin-owned paths and `host.fs` access only.

The installed package source fixes its files under `os.homedir()`. These paths are under the isolated home shown above:

- macOS and Linux: `~/.codeterm/teams-client/m365-home/.cli-m365-msal.json`, `.cli-m365-connection.json`, and `.cli-m365-all-connections.json`.
- Windows: `%USERPROFILE%\.codeterm\teams-client\m365-home\.cli-m365-msal.json`, `.cli-m365-connection.json`, and `.cli-m365-all-connections.json`.

The pinned MSAL serializer uses named token-type maps and runtime-generated keys. The access-token part of its JSON shape is:

```json
{
  "AccessToken": {
    "<runtime-generated composite key>": {
      "clientId": "<client id>",
      "credentialType": "AccessToken",
      "environment": "<cloud host>",
      "homeAccountId": "<account id>",
      "realm": "<tenant id>",
      "tokenType": "Bearer",
      "target": "<scopes>",
      "secret": "[redacted]"
    }
  }
}
```

That composite key depends on client ID, credential type, environment, home account ID, realm, token type, and target, so no static dotted path reaches its `secret`; D5 resolves to (a). The connection cache separately stores a current connection object with `identityId`, `identityTenantId`, and `accessTokens["https://graph.microsoft.com"] = { expiresOn, accessToken }`. The all-connections cache is an array of connection objects. The dotted resolver cannot address the Graph resource key because its periods are path separators, or records in the all-connections array because it has no array indexing. This implementation therefore makes no direct Graph request and does not inject a bearer header; m365 owns all Graph reads. The three files are declared as credentials without secret mappings so the host denies plugin `readFile` access. `credentialPublic` exposes only `identityId` as the account id, UPN, and tenant id as separate fields. A pinned Node helper asks m365's own `Auth` module for account metadata and emits only expiry and non-secret identity fields; it never emits an access-token value.

Sign-in uses the `appId` setting, by default `14d82eec-204b-4c2f-b7e8-296a70dab67e` (Microsoft Graph Command Line Tools), a Microsoft public client that accepts the `http://localhost` loopback redirect and device code. The Teams desktop/mobile client ID `1fec8e78-bce4-4aaf-ab1b-5451cc387264` stays selectable, but in the owner's tenant Microsoft rejected its loopback link with AADSTS50011 (redirect URI does not match) and its device code with `invalid_grant`. Any other public-client GUID can be set as `appId` in config.yaml; an invalid value falls back to the default. m365 passes it as `--appId`; the plugin creates no Entra app registration. m365 requests `https://graph.microsoft.com/.default`, so the token carries only the delegated permissions already consented for that app: `Chat.ReadWrite` and `ChatMessage.Send` must be approved for it once, by the owner if the tenant allows user consent, otherwise by a tenant administrator. After a sign-in the plugin probes `GET /me/chats?$top=1`; a consent error (AADSTS65001, AADSTS90094, admin approval, or Graph's missing-scope 403) ends the sign-in as `consent-required` with Microsoft's error line quoted (token-shaped text redacted) and the app id to approve. It is final, never retried in a loop. `wrong-client-redirect` (AADSTS50011, AADSTS500113) and `loopback-unavailable` (the localhost listener could not open), when m365 reports them, switch the sign-in to device code once and set `fallbackFrom`; a refused device code ends the sign-in. A redirect mismatch shown only in the browser never reaches m365, so the owner runs `login --device-code` or **Use a code instead** in the view. The plugin never lets m365 open a browser: m365 runs with this plugin's isolated HOME/APPDATA/LOCALAPPDATA, and a browser launched from it inherits them and starts on an empty profile (Zen on Windows showed its first-run screen, then a blank window). A small node wrapper replaces m365's browser opener with a `codeterm-signin: url` log line, so the authorize URL reaches chat and the view as `signInUrl` and the owner opens it in their usual browser on the same computer, where the localhost redirect completes. The wrapper exits, releasing its loopback listener, when `login.lease` stops holding its nonce (a new `login`, `logout`, or expiry) or after 10 minutes. The owner must confirm the resolved account and tenant, whether a consent prompt appeared, and that the live cache contents match the source-verified paths and composite-key shape.

Sending goes through the isolated m365 CLI so it owns token refresh: `m365 request --url https://graph.microsoft.com/v1.0/chats/<immutable-id>/messages --method post --content-type application/json --body @<file> --output json`. The message body is staged in a plugin-owned file and removed after the call, because m365 loads any option value that starts with `@` from disk and Windows runs m365 through a `.cmd` shim, so message text in argv would be neither literal nor safe. Graph returns the created chatMessage, and the plugin records its `id` as `graphMessageId`. No bearer token or other credential is passed in argv.

The Graph v1.0 `POST /chats/{chat-id}/messages` endpoint requires delegated `ChatMessage.Send` for a work/school account; broader delegated permissions include `Chat.ReadWrite` and `Group.ReadWrite.All`. A personal Microsoft account is unsupported for delegated `ChatMessage.Send` on that endpoint. `Teamwork.Migrate.All` is the Application-type permission for the import flow and requires the target chat to be in migration mode, so it is not a substitute for delegated send.

`chats [query]` lists the signed-in account's chats from `GET /me/chats?$expand=members&$top=50`, titled by topic or by the other members' names, with chat type, members, and member emails. With a query (a person's name or email, or a topic; Latin names also match Cyrillic ones), it returns the single `match`, or `ambiguous: true` with `candidates`. `preview <chat-id> <text>` is an optional dry run: it resolves the sender (account id and tenant), the chat, and the exact text, and says whether the owner's restriction would allow an agent send. It writes no attempt and sends nothing.

Sending works like a normal Teams client acting for the owner: `send` delivers to any chat the signed-in account can write to, with no setup or approval. The view has an optional **Restrict agent sends** setting, off by default. With "Only these chats" selected, an agent `send` to any other chat returns `chat-not-allowed` naming the setting; sends the owner makes from the view are never restricted. The setting lives in `~/.codeterm/teams-client/send-scope.json` and can only be changed from the view. A missing file means all chats; a file that cannot be read restricts the agent to no chats until the owner saves the setting again. A caller should pass `--key`; otherwise the key is the nonce of a matching earlier preview, or a fresh key returned in the result. A success without a Graph message id is recorded as `unknown`, never as sent.

The outbox is stored separately at `~/.codeterm/teams-client/outbox.json`; it stores identity and destination, a SHA-256 payload hash, timestamps, attempt count, state, and any returned Graph message id, never the message text. The state names match the Telegram send contract: `pending`, `sent`, `rate_limited`, `failed`, and `unknown`. A pending attempt is persisted before invoking m365. A recorded `sent` key returns its saved result without another command. The pinned m365 CLI 11.11.0 is downloaded with `npm pack`, checked locally against its pinned SHA-512, and installed from that local tarball with `--ignore-scripts`; it is never installed globally. The CLI consumes Graph's `Retry-After` header itself and retries 429/503 inside its subprocess; the plugin cannot observe that header or control those internal attempts. A throttled subprocess may pause for about 10 seconds or more without output, so the view explicitly tells the owner to wait for the result. If m365 ultimately surfaces a 429 or 503, the plugin records `unknown`, since one of its internal attempts may already have delivered, and refuses that key on later invocations. The `rate_limited` state remains in the shared state vocabulary for contract parity, but this transport does not create it or schedule a deadline. A definitive `failed` attempt can be retried only on a later caller invocation. Revoked refresh token (`refresh-token-revoked`), missing or withdrawn consent (`consent-required`), Conditional Access (`conditional-access-blocked`), and newly required MFA (`mfa-required`) surface the existing actionable reauthentication state and never receive a retry deadline. An ambiguous process start, timeout, lost result, or unrecordable success remains `unknown`; that key is refused and the owner must inspect the chat before deciding what to do.

Delivery guarantee: duplicate suppression is best-effort across process boundaries. The local ledger suppresses a repeated send for a key after its `sent` result is recorded, and it fails closed for the same key after an ambiguous outcome. It cannot see or prevent m365's internal retries: if Graph accepted a throttled request but its response was lost, an internal retry can create a duplicate before the CLI returns. The m365 CLI does not expose Graph's message id on success, and Graph plus the local file ledger cannot provide exactly-once delivery. A crash after Graph accepts a message but before the ledger records `sent` can leave an `unknown` attempt; the plugin will not resend that key, but an operator could still create a separate key and cause a duplicate.

The default app id is Microsoft Graph Command Line Tools with the loopback link first and device code as the fallback. No Entra app registration is created by this plugin.

For guided setup, use the plugin page header's **Configure with AI** button. The helper agent works in its chat: it runs `codeterm plugin teams-client login` (the first run installs the pinned m365 CLI), and polls `codeterm plugin teams-client login-status`. Agent sign-in uses the browser authorization-code flow first: `login-status` returns `signIn: "link"` with `signInUrl`, and the agent shows it in chat as a clickable link to open in your usual browser on this computer. Running `login` again cancels the pending sign-in and returns a fresh link; an unused link ends as `sign-in-expired` after 10 minutes. `login --device-code` (or an automatic fallback) returns `signIn: "device-code"` with `signInUrl` and `deviceCode`, and the agent shows both prominently. The agent keeps polling until sign-in is done and confirms with `health` and `accounts`. Results carry `appId`. The Teams Client view shows the same link or code, with **Sign in again** and **Use a code instead**.

Agent verbs are `login [--device-code]`, `login-status`, `accounts`, `use <account-id>`, `chats [query]`, `history <chat-id> [n]`, `health`, `preview <chat-id> <text>`, `send <chat-id> [--key <idempotency-key>] <text>`, and `logout`. The host grants `agent_commands` after installation. Chat IDs are immutable Graph IDs; history is bounded to 50 messages and 32 KiB. Message bodies are untrusted text and are never executed, routed as provenance, or exported to `codeterm mem`.

To reverse the setup, first use `logout` so m365 clears the token files. On macOS and Linux, run `npm uninstall --prefix "$HOME/.codeterm/teams-client/runtime/m365" @pnp/cli-microsoft365`, then remove the plugin-owned data root with `rm -rf "$HOME/.codeterm/teams-client"`. In PowerShell on Windows, run `npm uninstall --prefix "$env:USERPROFILE\.codeterm\teams-client\runtime\m365" @pnp/cli-microsoft365`, then remove that plugin-owned data root with `Remove-Item -Recurse -Force "$env:USERPROFILE\.codeterm\teams-client"`. These commands do not touch the owner's normal m365 profile.
